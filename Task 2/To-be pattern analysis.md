## Анализ паттернов и архитектурных стилей для новых интеграций TO-BE

### 1\. Мобильное приложение → API Gateway

**Паттерн:** API Gateway + Backend for Frontend (BFF)

**Архитектурный стиль:** Шлюзовой архитектурный стиль (Gateway Architecture) + Асинхронная коммуникация через Event Bus

**Почему выбран:**

* Мобильное приложение требует единой точки входа для всех запросов (запись, оплата, анализы, полисы)
* Необходимо скрыть от клиента сложность внутренней архитектуры и legacy-систем
* Требуется централизованное применение сквозных функций: rate limiting, идемпотентность, аутентификация
* Запросы, не требующие синхронного ответа (уведомления, обновление кэша), отправляются асинхронно через Event Bus

**Как решает проблемы AS-IS:**

* INT-005 (дубли записей) → идемпотентность на уровне Gateway
* INT-003 (1С падает на >50 rps) → rate limiting защищает 1С
* Отсутствие мониторинга → единая точка сбора метрик

### 2\. Мобильное приложение → Auth Service (через API Gateway)

**Паттерн:** JWT Token Authentication + OAuth 2.0 Authorization Code Flow

**Архитектурный стиль:** Безопасный шлюз (Security Gateway) + Асинхронная валидация токенов

**Почему выбран:**

* Решает проблему критической уязвимости, требующей централизованную аутентификацию
* JWT позволяет передавать данные о пациенте между сервисами без повторной аутентификации
* OAuth 2.0 обеспечивает стандартный протокол авторизации для мобильного приложения
* Асинхронная валидация токенов через Event Bus для снижения нагрузки на Auth Service

**Почему не legacy-решение:**

* 1С и LIS не поддерживают современные протоколы аутентификации
* Legacy-системы работают с собственными сессиями, что приводит к уязвимостям (SD-007)

**Как именно работает комбинация:**\\

1. Мобильное приложение отправляет логин/пароль на API Gateway (синхронно)
2. Gateway перенаправляет запрос в Auth Service
3. Auth Service проверяет credentials, возвращает JWT-токен
4. API Gateway кэширует публичный ключ для валидации всех последующих запросов
5. При истечении токена --- асинхронный запрос на обновление через Event Bus
6. Каждый запрос к legacy-системам содержит JWT, который валидируется на API Gateway

### 3\. API Gateway → Billing Service + Payment Gateway (Saga Pattern)

**Паттерн:** Saga Pattern (Choreography-based Saga) + Idempotency Key + Event-Driven

**Архитектурный стиль:** Распределённые транзакции (Distributed Transactions) + Асинхронная координация через Event Bus

**Почему выбран:**

* INT-001 (деньги списаны, статус не фиксирован) - требуется атомарность оплаты и записи
* SD-009 (двойное списание) - отсутствие идемпотентности
* Нельзя использовать ACID-транзакции, так как платежный шлюз - внешняя система
* Необходима асинхронная координация между сервисами для обеспечения отказоустойчивости

**Почему Choreography, а не Orchestration:**

* У нас уже есть Event Bus (Kafka) для асинхронных событий
* Choreography лучше подходит для слабо связанных систем
* Orchestration создал бы единую точку отказа (orchestrator)
* Kafka гарантирует доставку событий, что критично для Saga

**Как именно работает комбинация:**  
1. API Gateway создаёт уникальный idempotency\_key для каждого платежа(синхронно)  
2. Billing Service публикует событие PaymentInitiated в Kafka(асинхронно)  
3. Billing Service отправляет запрос на списание в Payment Gateway (синхронно с внешней системой)  
4. Payment Gateway возвращает confirmation + сохраняет ключ (гарантия однократного списания)  
5. Billing Service публикует событие PaymentCompleted в Kafka (асинхронно)  
6. Scheduler подписывается на событие и подтверждает запись  
7. Если Scheduler не смог подтвердить (например, слот уже занят) - публикуется PaymentRefundRequired  
8. Billing Service подписывается на событие и инициирует возврат средств (компенсирующая транзакция)

**Комбинация паттернов:**

Синхронно: API Gateway → Billing Service (REST); Billing Service → Payment Gateway (REST)

Асинхронно: Billing Service ↔ Kafka (Event Bus); Scheduler ↔ Kafka (Event Bus)

### 4\. Кэширование: API Gateway → Redis Cache → 1С (Polis)

**Паттерн:** Cache-Aside (Lazy Loading) + TTL-based Invalidation + Write-Through Cache для обновлений

**Архитектурный стиль:** Кэширующая архитектура (Caching Architecture) + Асинхронное обновление кэша через Event Bus

**Почему выбран:**

* INT-003 (1С падает на пиках >50 rps) - 1С не справляется с нагрузкой
* SD-001 (1С отвечает дольше 30 секунд) --- высокая задержка
* Данные полисов ДМС меняются редко (обычно раз в год), что делает кэширование эффективным
* Асинхронное обновление кэша через Event Bus позволяет не блокировать запросы

**Почему Cache-Aside + Write-Through:**

* 1С - внешняя система, которую нельзя модифицировать для автоматического обновления кэша
* Cache-Aside позволяет контролировать, когда и как обновлять кэш
* Write-Through используется для немедленного обновления кэша при изменении полиса (если изменение инициировано через API Gateway)

**Как именно работает комбинация:**\\

1. Запрос проверки полиса приходит в API Gateway\\
2. Gateway обращается в Redis с ключом polis:{patient\_id} (синхронно)  
3. Если есть (cache hit, \~95%): возвращаем данные немедленно  
4. Если нет (cache miss):
* Запрос к 1С (HTTP-шлюз) (синхронно)
* Результат публикуется в Kafka для асинхронного обновления кэша
* Sync Service подписывается на событие и сохраняет в Redis (асинхронно)
* Возвращается ответ пациенту (синхронно)

5\. При ошибке 1С (503) возвращаем данные из кэша (stale data) -лучше, чем ошибка

**Комбинация паттернов:**

Синхронно: Gateway → Redis (cache read); Gateway → 1С (cache miss, прямой запрос)

Асинхронно: Gateway → Kafka → Sync Service → Redis (cache update)

### 5\. Event Bus (Kafka) → Сервисы

**Паттерн:** Event-Driven Architecture (EDA) + Publish/Subscribe + Competing Consumers

**Архитектурный стиль:** Событийно-ориентированная архитектура с гарантированной доставкой

**Почему выбран:**

* SD-006 (пуши не приходят из-за переполнения очереди RabbitMQ)- текущий RabbitMQ ненадёжен
* Требуется гарантированная доставка сообщений для критических событий (оплата, запись)
* Необходима обработка пиковых нагрузок (500 → 50 000 пользователей)
* Competing Consumers позволяет горизонтально масштабировать обработчики

**Почему Kafka, а не RabbitMQ (как в AS-IS):**

|Характеристика|RabbitMQ (AS-IS)|Kafka (TO-BE)|
|-|-|-|
|Хранение сообщений   | В памяти (теряются при падении)|На диске (репликация)|
|Гарантия доставки|At-most-once (ошибка 404)|Exactly-once|
|производительность|\~10k msg/sec|\~1M msg/sec|
|пиковые нагрузки|Падает|выдерживает|
|масштабирование|сложное (очереди)|простое (партиции +  группы потребителей)|



**Как именно работает комбинация:**  
1. **Система расписания** публикует событие AppointmentCreated в Kafka(асинхронно)  
2. **Notification Service** (consumer group из 3 инстансов) потребляет событие и отправляет push/email/SMS  
3. **Sync Service** (другая consumer group) потребляет то же событие для синхронизации с legacy  
4. **Billing Service** может потреблять событие для обновления статуса платежа  
5. Kafka гарантирует хранение сообщения до его успешного потребления всеми подписчиками  
6. При падении consumer --- другой инстанс подхватывает обработку (Competing Consumers)

**Комбинация паттернов:**

Publish/Subscribe: Одно событие → несколько consumer groups

Competing Consumers: Одна consumer group → несколько инстансов

### 6\. Data Sync Service → LIS (SOAP + FTP)

**Паттерн:** Polling Consumer + Retry Pattern + Dead Letter Channel +Circuit Breaker

**Архитектурный стиль:** Интеграционный адаптер (Adapter Pattern) + Асинхронная обработка ошибок через Event Bus

**Почему выбран:**

* INT-002 (FTP падает с ошибкой 425) --- отсутствие автоматических повторов
* INT-008 (дубли XML-файлов) --- некорректная обработка идемпотентности
* LIS --- legacy-система с устаревшими протоколами (SOAP, FTP), которую нельзя модифицировать
* Circuit Breaker защищает LIS от перегрузки при множественных ошибках

**Почему именно Polling, а не Event-Driven:**

* LIS не поддерживает webhooks или push-уведомления
* LIS доступен только для просмотра (лаборанты не могут менять логику)
* Polling с разумным интервалом (30 секунд) достаточен для анализов
* Circuit Breaker автоматически отключает poll при 5 последовательных ошибках

**Как именно работает комбинация:**  
1. Sync Service каждые 30 секунд опрашивает LIS через SOAP на наличие новых результатов (асинхронно, фоновый процесс)  
2. При 5 последовательных ошибках Circuit Breaker размыкается (отключает poll на 5 минут)  
3. При обнаружении новых данных --- загружает через FTP с использованием retry:

* 1-я попытка: сразу
* 2-я попытка: через 5 секунд
* 3-я попытка: через 15 секунд 

4\. После успешной загрузки --- проверяет уникальность (deduplication) по ID анализа  
5. Публикует событие AnalysisReady в Kafka (асинхронно)  
6. Sync Service (другой consumer) подписывается на событие и обновляет CRM через REST API  
7. При 3-х неудачных попытках → сообщение в Dead Letter Queue  
8. DLQ автоматически повторяет попытку через час 
9. Если всё ещё ошибка → алерт в Monitoring \& Tracing

**Комбинация паттернов:**

Polling: Sync Service → LIS (SOAP) --- фоновый процесс

Retry: FTP загрузка с exponential backoff (5c, 15c, 45c)

Circuit Breaker: Отключение poll при 5 ошибках

Event-Driven: Sync Service → Kafka (публикация AnalysisReady); Kafka → Sync Service → CRM (обновление)

Dead Letter Channel: При 3+ ошибках → DLQ → Manual Recovery

### 7\. Monitoring \& Tracing → Все компоненты

**Паттерн:** Distributed Tracing (W3C Trace Context) + Metrics Collection + Centralized Logging + Health Checks

**Архитектурный стиль:** Observability Architecture (Наблюдаемость) с асинхронным сбором данных

**Почему выбран:**

* INT-007 (отсутствие distributed tracing -"сложно найти корень сбоя")
* SD-002 (ошибка "Booking not found for paymentID") - без tracing невозможно понять, на каком этапе потерялась связь
* Требуется обеспечить SLO: "99.95% доступности" и "время отклика < 1 секунды"
* Асинхронный сбор метрик не влияет на производительность продакшн-систем



**Почему Jaeger + Prometheus + OpenTelemetry:**

**OpenTelemetry:** Стандартный протокол для сбора трасс и метрик, асинхронно (background)
**Jaeger**:Распределённая трассировка (путь запроса), асинхронно (через OpenTelemetry)

**Prometheus**: Pull-based метрики (количество,ошибки, задержки)  Pull (Prometheus опрашивает сервисы)

**Grafana**: Визуализация дашбордов, синхронно (запрос-ответ)



**Как именно работает комбинация:**

1. Каждый сервис (API Gateway, Billing, Scheduler и т.д.) экспортирует трассы через OpenTelemetry
2. Каждый запрос имеет уникальный trace\_id, который передаётся между сервисами
3. OpenTelemetry Collector асинхронно отправляет трассы в Jaeger (не блокирует запросы)
4. Prometheus каждые 15 секунд (pull) собирает метрики: request\_count, error\_count, response\_time\_ms
5. Алерты: при превышении порогов (99% запросов > 1 секунды, доступность < 99.95%)
6. Health checks: каждый сервис экспортирует /health endpoint(используется Load Balancer)

**Асинхронный сбор:**

Трассы: OpenTelemetry → Jaeger (асинхронно, через Collector)

Метрики: Prometheus → Pull от сервисов (каждые 15 секунд)

Логи: Fluentd → Elasticsearch (асинхронно)

Алерты: Prometheus → Alertmanager → PagerDuty/Slack

**Комбинация паттернов:**

Синхронно: Prometheus Pull (15s), Health Checks

Асинхронно: OpenTelemetry → Jaeger, Fluentd → ES, Alerts
